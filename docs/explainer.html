The PR relay

How Tagreeve (formerly Pingwright) gets built: every change is a small pull request that passes through a relay of separate agents. One builds it, one tests it from scratch, one tries to break it, one fixes what they found, and only then does an agent merge it, once the gate and the merge-safety check clear it, or you do. No agent ever checks its own work.

The loop, in one picture

Test and review run at the same time, on the same commit. The dashed loop can go round up to four times. After that, a person decides. When the change is clean, one minor pass fixes the small findings and a short check keeps or reverts it. Then a docs writer updates the docs it affects, and a short test and review check that commit before the PR opens. When a PR's work ends, a small agent deletes its clones and finished worktrees.

Who does what

BUILDER

Writes the change

Follows one entry in the plan. Adds a test, then breaks the feature on purpose to prove the test notices.

TESTER

Starts from scratch

Downloads a fresh copy and runs every check. It changes nothing, so "works on my machine" can't slip through.

REVIEWER

Looks for trouble

A stronger model reads the change against the plan and the design. It ranks each problem: blocker, major or minor.

QA

Uses it like you would

When the plan asks for it, a separate agent runs the finished feature: the main case, empty and bad input, combinations with other options, and what the docs promise.

PRODUCT CHECK

Keeps the plan on course

Before anything is built, an Opus reviewer checks every plan entry against the product's goals and non-goals. If something widens the product, like an MCP server on a CLI tool, it stops and asks you.

ARCHITECT

Guards the shape

An Opus reviewer lists the new concepts a PR brings in and checks them against the architecture. Small mismatches become fixes. If the architecture itself should change, it stops and asks you.

TRIAGER

Sizes up a quick fix

For a single issue with no plan, an Opus reviewer reads the issue, the code and the goals. It decides to build, to plan properly, or to decline. A change of size L or risk high becomes a plan. A small, low-risk change gets lighter checks.

MERGE SAFETY

Decides who merges

A script first checks the changed files against the gated paths. For the rest, a read-only Opus agent answers "safe" or "person". Only a PR that passes both is merged by an agent. A rerun never is.

EVALUATOR

Reviews the run itself

When a wave ends, it reads what happened and writes feedback about the pipeline. You approve it, and a script files it as issues. For another repo, a redactor removes that repo's details first.

FIXER

Repairs, or argues back

Fixes blockers and majors. After sign-off it also makes one capped pass over the minors in files the PR already changes. A tester and a reviewer check only that pass, and a failed check reverts it with a new commit. If it thinks a finding is wrong, it has to say why, with evidence.

DOCS WRITER

Keeps the docs true

After the review passes, it reads the change and fixes every page it makes wrong: README, docs and the docs site. A separate reviewer checks its edits.

PR AGENT

Talks to the bots

Opens the pull request, files small findings as issues for later, and replies to every review-bot comment.

ROUTINE

Triages feedback each hour

An optional hourly job reads the open feedback issues of a repo and decides for each one: build, plan or decline. It starts in observe mode, which changes nothing on GitHub. It never writes code, opens a PR or merges. See docs/routine.md.

YOU

Make the calls

Approve the plan, approve rule changes, and own publishing. Agents merge only a PR that passed the gated-path check and the merge-safety agent. You merge every other PR. You make the first release. After that, when the repo's settings turn on automatic release, a script makes the release after the last wave, once its checks pass. The script never publishes a package.

Ways to make it faster and cheaper

Applied in the skill repo, alfhen/agent-pr-pipeline; Tagreeve's own builds use them from 0.4.0 on. Each keeps the rule that no agent checks its own work.

  • Replace the land agent with a script.It mostly waits for CI. A script can wait and merge; an agent is needed only when CI fails or the PR conflicts.Saves 1 of 5 agent runs per PR.
  • Let a script wait for the review bots.The PR agent polls for up to 20 minutes. A script can wait, and wake a small agent only when there are comments to answer.Saves most of the PR agent's time; it could run on Haiku or Sonnet at low effort.
  • Test smarter, not twice.The tester could run install, lint, types, unit tests and only the PR's own e2e files, and leave the full e2e to CI, which already runs it on four shards. That also removes most of the flaky failures caused by many browsers at once.About 10 minutes off each round.
  • Set effort per step.Reviewer: Opus at high, as now. Builder and fixer: Sonnet at medium. Tester and land: low. Docs-only PRs: a Sonnet reviewer at high instead of Opus.Fewer tokens on routine steps, same scrutiny where it matters.
  • Give each role its own agent.The role's rules go in the agent definition, with the smallest set of tools the role needs. Agents of one role share the cached tools and rules; each agent's own turns read from the cache.In a test wave, 85% of all input came from the cache.
  • Load skills only where they help.A skill adds thousands of tokens to every agent that loads it, every round. Pair a skill with the steps where it changes the result, such as a security review only for sensitive PRs.No skill tokens on steps that do not need them.
  • Cap plan reviews at three rounds.Plans took 4 to 5 rounds. After three, fix what is left by hand, as we did for the 0.3.0 plan's last finding.Up to half a plan's cost.

Why it works

  • 1

    Small pieces. Each PR does one thing from the plan, so a reviewer can hold all of it in mind.

  • 2

    No marking your own homework. The builder, tester and reviewer are different agents with different instructions. Mistakes one makes, another tends to catch.

  • 3

    Tests that can fail. Every change needs a test that fails when the change is removed. "Passes for the wrong reason" is the most common real problem reviewers find.

  • 4

    Waves. PRs in the same wave can touch the same file when they edit different parts of it. PRs that edit the same part go in different waves, so several are built at once without stepping on each other.

  • 5

    Small stuff waits. Minor findings get one capped fix pass after sign-off. The rest go into one checklist comment on the PR. An issue is filed only for a minor that has a real effect, so the loop doesn't drag on over nits.

Where you step in

  • You agree the plan before anything is built.
  • You approve anything that changes a hard rule. For example, payments on real stores stay a human step unless you sign off.
  • You merge every gated PR, any PR the merge-safety agent called person, and every rerun. Use --person for a merge you ask for.
  • Agents merge only the other PRs, with the :auto land value. A rerun never gets :auto. Merges need green CI and a review bot that approved, or whose comments were all answered with nothing new raised.
  • Publishing to npm is yours, with your one-time code.
