The PR relay

How Pingwright gets built: every change is a small pull request that passes through a relay of separate agents. One builds it, one tests it from scratch, one tries to break it, one fixes what they found, and only then do you merge it. No agent ever checks its own work.

The loop, in one picture

Test and review run at the same time, on the same commit. The dashed loop can go round up to four times. After that, a person decides.

Who does what

BUILDER

Writes the change

Follows one entry in the plan. Adds a test, then breaks the feature on purpose to prove the test notices.

TESTER

Starts from scratch

Downloads a fresh copy and runs every check. It changes nothing, so "works on my machine" can't slip through.

REVIEWER

Looks for trouble

A stronger model reads the change against the plan and the design. It ranks each problem: blocker, major or minor.

FIXER

Repairs, or argues back

Fixes blockers and majors. If it thinks a finding is wrong, it has to say why, with evidence.

PR AGENT

Talks to the bots

Opens the pull request, files small findings as issues for later, and replies to every review-bot comment.

YOU

Make the calls

Approve the plan, approve rule changes, and own merging, releases and publishing. Agents never merge.

Follow one real PR

Why it works

  • 1

    Small pieces. Each PR does one thing from the plan, so a reviewer can hold all of it in mind.

  • 2

    No marking your own homework. The builder, tester and reviewer are different agents with different instructions. Mistakes one makes, another tends to catch.

  • 3

    Tests that can fail. Every change needs a test that fails when the change is removed. "Passes for the wrong reason" is the most common real problem reviewers find.

  • 4

    Waves. PRs in the same wave touch different files, so several are built at once without stepping on each other.

  • 5

    Small stuff waits. Minor findings become issues and get fixed in batches later, so the loop doesn't drag on over nits.

Where you step in

  • You agree the plan before anything is built.
  • You approve anything that changes a hard rule. For example, payments on real stores stay a human step unless you sign off.
  • You see every merge happen in your own session. Merges need green CI and a bot's approval.
  • Publishing to npm is yours, with your one-time code.
